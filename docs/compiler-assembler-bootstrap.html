Component Architecture

prisc+x VM (prisc+x.c)

The foundation VM that interprets .pal programs. Key constraints:

ResourceLimit
Integer registersx0–x15 (16 total)
String registerss0–s31 (4KB each)
Data memory (dmem)4096 slots
Instruction limit4096
Labels in .pal128
Critical constraint: The .pal VM's add instruction only accepts register operands (add rd, rs1, rs2). To add an immediate value, you MUST use addi rd, rs1, imm. Using add with a numeric literal silently fails (sscanf doesn't match the number as a register) and becomes a no-op. This was the root cause of a bug affecting 6 label-address computations.

Compiler (cc.pal)

A line-by-line pattern-matching C-to-RV32I compiler. It does NOT build a full AST — instead it matches each source line against known patterns and emits assembly directly.

Assembler (asm.pal)

Reads RV32I assembly text (with labels) and encodes instructions into 32-bit binary values. Uses a two-pass algorithm:

Pass 1: Scan all lines, detect labels (lines containing :), and store the byte address of each label at dmem[100+label_index]. The instruction counter (dmem[2]) increments by 4 for each instruction line, but NOT for labels.
Pass 2: Re-scan lines, pattern-match each instruction to determine its type, compute the binary encoding (including branch/jump offsets using label addresses from dmem), and output via builtin_out.

Label Storage and Addressing

Labels are stored in dmem[100] through dmem[100+N-1], where N is the number of labels:

Branch/Jump Offset Computation

For branch (B-type) and jump (J-type) instructions, the offset is computed at runtime in asm.pal Pass 2:

# B-type (branch):
lw   x6, 0(x5)      # x6 = target label address (from dmem)
lw   x7, 2(x0)      # x7 = current instruction address
sub  x8, x6, x7     # x8 = offset = target - current

# Extract B-type immediate fields from offset:
srli x9, x8, 12; andi x9, x9, 1   # imm[12]
srli x9, x8, 5;  andi x9, x9, 63  # imm[10:5]
srli x9, x8, 1;  andi x9, x9, 15  # imm[4:1]
srli x9, x8, 11; andi x9, x9, 1   # imm[11]

B-type layout: imm[12|10:5] rs2 rs1 funct3 imm[4:1|11] opcode

# J-type (jal):
# Same offset computation, different bit packing
srli x9, x8, 20; andi x9, x9, 1   # imm[20]
srli x9, x8, 12; andi x9, x9, 255 # imm[19:12]
srli x9, x8, 11; andi x9, x9, 1   # imm[11]
srli x9, x8, 1;  andi x9, x9, 1023 # imm[10:1]

J-type layout: imm[20|10:5|4:1|11|19:12] rd opcode (note: imm[10:1] packs bits 10:5 and 4:1 together)

Bug: Label Address Corruption

Bug: In Pass 1, label address computation used add x5, x5, 100 instead of addi x5, x5, 100. The .pal VM's add only accepts register operands — when 100 is passed as the third operand, sscanf fails to parse it as a register name, leaving the destination unchanged (effectively add x5, x5, x0).
Fix: Changed all 6 occurrences to addi x5, x_, 100 in asm.pal (lines 31, 306, 338, 372, 399, 426). This ensures the base address 100 is correctly added, so label addresses are stored at the right dmem locations.

No jal/jr/jalr or mul instructions. Function calls don't exist — all code is inlined linearly. Multiplication uses shift-add or repeated addition. The ret pseudo-instruction is encoded as jalr x0, x1, 0.

Pipeline Flow Walkthrough

1. Write C source in c_source.c — a subset C program with int main(), variable declarations, putint() calls, while loops, and if/else conditionals.
2. Run cc.pal on the prisc+x VM: ./prisc_x cc.pal — reads C source line-by-line, pattern-matches each line, emits RV32I assembly text to /tmp/cc_out.s
3. Run asm.pal on the prisc+x VM: ./prisc_x asm.pal — reads the assembly text, performs two-pass assembly (Pass 1: label resolution, Pass 2: instruction encoding), outputs 32-bit binary values via builtin_out
4. Collect binary values — the 42 output integers are the RV32I machine code, ready for execution on any RV32I emulator

Running the Full Bootstrap Pipeline

# 1. Write C source
cat > c_source.c 'EOF'
int main() {
    int x = 5;
    int y = 3;
    putint(x + y);
    putint(x - y);
    putint(x * y);
    int i = 0;
    while (i < 3) {
        putint(i);
        i = i + 1;
    }
    int z = 10;
    if (z > 5) {
        putint(1);
    } else {
        putint(0);
    }
    return 0;
}
EOF'

# 2. Build the VM
gcc -O2 -o prisc_x prisc+x.c

# 3. Run the compiler (C → assembly text)
./prisc_x cc.pal
# Output: /tmp/cc_out.s

# 4. Run the assembler (assembly text → RV32I binary)
./prisc_x asm.pal
# Output: 42 encoded instruction values via builtin_out

Stack Layout (cc.pal)

The compiler emits stack frames with variables at fixed offsets from sp:

main:
  addi sp, sp, -32        # Allocate 32 bytes
  sw   ra, 28(sp)         # Save return address
  # x = -4(sp), y = -8(sp), i = -12(sp)
  # z = -16(sp), a = -20(sp), b = -24(sp)
  # c = -28(sp), d = -32(sp)

Key Design Decisions

1. Pattern Matching Over AST

Instead of building an Abstract Syntax Tree, cc.pal uses direct pattern matching via sfind. This works because the C subset is very limited — each line matches exactly one known pattern.

2. Label Index Assumptions

The assembler uses hardcoded label indices (0=loop_start, 1=loop_body, etc.) rather than dynamic lookup. This avoids the need for a symbol table while trading flexibility for simplicity.

3. Two-Pass Label Resolution

Labels are resolved in Pass 1 and stored at dmem[100+N]. Pass 2 computes branch/jump offsets as target_addr - current_addr, enabling both forward and backward jumps.

4. Immediate Encoding in .pal

The .pal VM enforces a strict distinction:

InstructionOperandsExample
addi rd, rs1, imm2 registers + immediateaddi x5, x3, 100
add rd, rs1, rs23 registers onlyadd x10, x10, x11

Passing an immediate to add silently fails — the third operand must be a register.

5. Output via builtin_out

The assembler outputs each encoded instruction as a signed 32-bit integer via builtin_out. These values are the RV32I machine code bytes, ready for execution.
